# Обновления приложения

В **Настройках → Обновления** отображается установленная версия и кнопка «Проверить обновления». Проверка выполняется по запросу, без аккаунта GitHub и без отдельного сервера Лада.

При наличии новой версии можно посмотреть изменения и скачать файл. Музыка продолжает играть во время загрузки. Установка начинается только по нажатию пользователя; на компьютере Лад перезапускается, на Android открывается системное окно установки. Вход, оформление и очередь сохраняются в существующем профиле.

При первом обновлении Android может попросить разрешить Ладу установку приложений. После разрешения вернись в Лад. При отмене системного установщика можно повторить установку из того же раздела.

Если скачивание прервалось, текущий Лад продолжает работать. Повторная загрузка начинается заново. Загруженное обновление доступно после перезапуска приложения. Для установки требуется свободное место под файл, распакованную новую версию и резервную копию desktop-приложения.

macOS и Windows используют отдельный процесс установки. Он ждёт закрытия приложения, обновляет его и ожидает подтверждения запуска музыкального сервиса и интерфейса. При неудаче предпринимается возврат предыдущей копии. На Android установку и сохранение данных выполняет система. Папка desktop-приложения должна быть доступна для записи текущему пользователю.

## Версии

С версии **0.3.0** все четыре приложения получают единый номер `major.minor.patch`. Источник номера — [`release-config.json`](../release-config.json). Внутренние Android `versionCode` растут независимо и никогда не уменьшаются. `scripts/sync-version.py` применяет номер к приложениям; CI проверяет отсутствие расхождений.

Релизы 0.1.0 и их приложения были выпущены до появления обновлялки: первую версию 0.3.0 нужно установить вручную поверх существующей. Следующие версии можно получать из приложения.

## Доверие к обновлению

Все клиенты загружают `updates.json` из последнего опубликованного GitHub Release. Этот файл содержит подписанный Ed25519 payload: версии платформ, описание изменений, имена файлов, размеры и SHA-256. Публичный ключ встроен в приложения; приватный ключ хранится отдельно от репозитория и артефактов.

Клиент проверяет подпись до использования ссылок, выбирает свою платформу и разрешает первоначальную ссылку только на файлы релизов `KiriDey0/Lad`. Перенаправления допускаются только на разрешённые HTTPS-домены GitHub. Размер и SHA-256 проверяются при скачивании и повторно перед установкой. Стабильная версия должна быть новее установленной; на Android дополнительно проверяются package ID, versionCode, versionName и совпадение сертификата APK.

Метаданные не содержат команд, которые клиент мог бы выполнить. Файлы установки обрабатываются заранее встроенными платформенными помощниками. Приватные ключи, OAuth-токены и cookies не передаются в запросах проверки обновлений.

GitHub получает обычные сетевые сведения, необходимые для выдачи файла, включая IP-адрес. Проверка не обращается к Яндексу и не передаёт историю прослушивания.

## Подготовка выпуска

1. Обнови `release-config.json` и changelog, запусти `python3 scripts/sync-version.py`.
2. Собери и проверь приложения, сохраняя прежние Android-ключи подписи.
3. Положи файлы с именами, указанными в `scripts/sign-release.cjs`, в каталог артефактов.
4. Выполни `node scripts/sign-release.cjs <каталог> <приватный-ключ> <файл-изменений>` в защищённой среде выпуска.
5. Добавь `updates.json`, исходники и контрольные суммы в draft Release. Перед публикацией проверь размеры и хэши загруженных файлов.

Смена публичного ключа требует отдельного плана миграции. Нельзя просто заменить ключ между релизами: существующие клиенты отвергнут новую подпись. Смена Android-сертификата также требует совместимой схемы миграции и проверки на поддерживаемых версиях ОС.
